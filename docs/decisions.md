# BrainChat builder calls

One line per choice the spec leaves to the builder or the plan rules on.

- Runtime: Windows Python 3.12 via `uv`, CPU only, because Ollama and Label Studio listen on Windows `127.0.0.1`, which WSL2's default NAT can't reach (differs from spec sections 10 and 13 on purpose).
- Data folder: `CHATBRAIN_DATA` must be set and absolute; there is no default.
- Data folder guard: refused when it is inside the repo or holds it, has a path segment starting with `OneDrive` (any case, so `OneDrive - <org>` too) or has a `.git` entry in itself or any ancestor; both the written and the resolved path are checked, and nothing is created on refusal.
- Label scheme: `config/labels_v1.json` is the only source of value lists; `scheme.load` rejects unknown keys, repeats and missing `display` or `help` entries.
- Scheme text: `display` is keyed by bare value; `help` is keyed by question key and by `<group>.<value>`, because `unclear` is both an aimed-at value and a not-sure reason.
- Agent guard: `AGENTS.md` (loaded by `CLAUDE.md`) is the guard, for every tool, shell commands included.
- Export format: strict JSON contracts `chatbrain-export/1`, `chatbrain-window-list/1` and `chatbrain-deletion-check/1` (`docs/export-format.md`); the deletion check lists every requested window with the messages still present, `[]` when none are, and a window it leaves out is left alone (ruling C2).
- SQLite store: `secure_delete=ON` and `journal_mode=DELETE`, plus `temp_store=MEMORY` and `foreign_keys=ON`; times are stored as fixed-width UTC text so SQL compares them correctly.
- Spread thresholds: in order, `few_posters` under 5 distinct posters, `chant` at a chant share >= 0.30, `repeated_emotes` at a top-emote share >= 0.40, `back_and_forth` at an `@s<N>` share >= 0.20, else `separate_messages`; shares are of messages and compared exactly; a chant is a normalised line of 2+ tokens said in 2+ messages; ties go to the smaller text or emote ID (`spread.py`).
- Import: a file imports in one transaction, all or nothing; windows whose `language` isn't exactly `en`, or whose text has expired (`text_expires_at <= now`), are skipped and counted; the source file is deleted as soon as the import commits, so the store is the only copy of text, and a file that can't be deleted then is retried by expiry (ruling C3).
- Import log: `imported_files` keeps the resolved, case-folded source path and every window ID in the file; expiry deletes a file found at a logged path only when every window in it is in that import's log.
- Expiry: `now == text_expires_at` is expired; messages go and the window turns `expired` in one transaction, `imported/` is emptied, then `VACUUM` runs on every expiry.
- Label Studio deletion: expiry deletes the tasks of every window whose text has expired, whatever its `text_state`, plus tasks a deletion check changed, one task at a time; each `ls_tasks` row goes once its delete succeeds, and `compact()` runs while a delete has not been compacted (rulings C4, C5); without a client the commands print how many are pending.
- Freshness gate: refuses with no check, a newest check more than 7 days old or more than 5 minutes in the future, or a window with text that no check from the last 7 days listed (rulings T1, B6); refusals give counts only.
- Command output: counts, file names and status only, never chat text or window IDs.
- Assignment: a window is blind iff `sha256("<seed>:<window_id>")` (UTF-8) mod 10000 < 2500; only windows that still have text and no assignment get a row, rows never change, and `--all-blind` (pilot mode) makes every new row blind.
- Repeats: picked iff `sha256("<seed>:repeat:<window_id>")` mod 10000 < 1000, due 3 + (that hash mod 5) days after the owner's first blind- or suggested-project label (`labels.created_at`, the annotation time, ruling C35); skipped while the due date is at or after `text_expires_at` or the text is gone, and never for synthetic labels, page fixes or a window that already has a repeat; rows never change.
- Rare picks: `pick-rare` is all or nothing (an unknown ID marks nothing and prints counts only), and the mark outlives the text. `assign`, `repeats` and `pick-rare` don't run the freshness gate: they never show text or ask for a suggestion or a label.
- Export coverage (B7): an import counts as a deletion check for the windows it adds, dated `min(exported_at, now)` and keeping the newer of an existing date; a duplicate window is covered only when the export still holds every message the store kept. A fresh import passes the gate with no check file.
- Gate order: no check or coverage at all, then a newest date more than 5 minutes ahead, then windows with text not covered in the last 7 days (count only), then a newest date more than 7 days old.
- Label Studio container: `heartexlabs/label-studio:1.23.2`, published as `127.0.0.1:14610:8080` (never on every address), data in `<data>/labelstudio`; `COLLECT_ANALYTICS`, `LATEST_VERSION_CHECK`, `SENTRY_DSN` and `FRONTEND_SENTRY_DSN` are switched off in `compose.yaml`, because 1.23 sends Sentry reports to Heartex by default.
- Label Studio client: loopback hosts only (`127.0.0.0/8`, `::1`, `localhost`), no proxies from the environment, no redirects; errors carry the HTTP status or exception type, never a body or the token.
- Label Studio auth: `LS_AUTH=pat` refreshes an access token at `POST /api/token/refresh/` (the trailing slash matters) every 4 minutes and once after a 401, sent as `Bearer`; `LS_AUTH=legacy` sends `Token <token>`. Checked against the 1.23.2 image source.
- Label Studio config (C17): the client is built only from `<CHATBRAIN_DATA>/.env` and only when the command runs on that real folder, so a `--data-dir` run never reaches the real Label Studio.
- Projects: `Chat Brain · Suggested`, `· Blind` and `· Repeat`, found by exact title (the real projects already exist under these titles, so they keep the old name); one annotation per task, no empty annotations, no annotation history, prelabels shown only in the suggested project.
- Labeling view (the Label Studio XML): built from `config/labels_v1.json` by `lstudio/config.label_config`, never written by hand, and sent to every project by `ls-setup` and `push`; each `<Choice>` shows the scheme's display text and stores the scheme value through `alias`, with its help as the hint; each question has a separate not-sure reasons field; hotkeys go on the 25 question values only; a blank tone is stored as `no_clear_tone`.
- Tasks: one task per import, and its `ls_tasks` row is written before the next import, so a crash leaves at most one untracked task; `push` adopts tasks Label Studio holds for known windows before importing and after a failed import, and counts tasks for unknown windows (they are never deleted automatically).
- Task data: window ID, each line's per-window speaker and text, and a counts line of numbers, emote IDs and the spread value only; message IDs, channel and stream never reach Label Studio.
- Push rules: a window goes to a project once, only while its text lives, only with an assignment (B12), and never after the owner labeled it there; blind and suggested follow the assignment, suggested also needs a `suggestions` row; repeats push only when due, shuffled, with no prediction and no earlier label (C15).
- Suggestion contract (Task 7): `suggestions.answers_json` holds `{"answers": {...}, "not_sure": {...}}` in the `validate_answers` shape; the newest row of a window is the one pushed and compared; an error row or an unusable answer pushes no prediction and syncs as `unsuggested`.
- Prelabel version: a suggested task's prediction carries `model_version = <teacher_model>/<prompt_version>`, and `push` points the project at the last version it pushed, because Label Studio shows one model version's predictions.
- Pull: an annotation becomes a label once (by `ls_annotation_id`); cancelled ones are skipped; a refused one is listed with a reason that names fields and rules only; `accepted` means both dicts equal the newest suggestion's after filling the blank tone; `created_at` is the annotation's own time as fixed-width UTC (C35).
- Pull before delete (B11): when expiry has Label Studio tasks to delete, it pulls every project first; if that pull fails the deletes still run and the command says how many deleted tasks had no stored label.
- Deletes: a task that is already gone (404) counts as deleted; the CLI says whether Label Studio was unreachable, refused, or answered without deleting.
- Export copies (B13): Label Studio writes a copy of every export, with live text, to `<data>/labelstudio/export`. `export_annotations` empties `export/` and `media/export/` there as soon as the answer has been read, even when the call fails, so the copies from pull, adoption and the B11 pull never wait for a compaction.
- Compaction: `compact()` empties `export/` and `media/export/` again, then runs `VACUUM` on Label Studio's SQLite database inside the container with `docker compose exec`.
- `ls-push` refuses while Label Studio deletions or compaction are pending, applies the waiting deletion-check files first (a refused file stops it, B10), then needs the freshness gate (C36).
- Teacher (Task 7): `qwen3:8b` by default (`--model` for others) through `POST /api/chat` with `format` = the reply schema, `stream` and `think` false, `num_ctx` 8192 and temperature 0; prompt version `cb_teacher_2026_11_06_v1`.
- Ollama gate (R3, C13): `ollama.check` needs a loopback base URL (`127.0.0.0/8`, `::1`, `localhost`, as for Label Studio), a client that reads no proxy settings and follows no redirects (on Windows httpx would otherwise take the system proxy from the registry, even for `127.0.0.1`), and `/api/version` 0.31.2 or newer, a pre-release of 0.31.2 counting as older.
- Teacher prompt: the rules (only what chat shows, not sure with reasons, never name anyone, never a cause, never identity or protected traits, a contested reading is `needs_review`), then every `help` definition; the user part is the counts line and `s<N>: text` lines with whitespace collapsed, and never the channel, stream or window ID.
- Teacher reply: `{question: {"value", "not_sure"}}` for every question, read like a Label Studio annotation (one or the other; a blank tone is `no_clear_tone`; values put in scheme order; repeats refused), then `validate_answers`; stored as `{"answers", "not_sure"}`.
- Teacher errors (T2): `timeout`, `bad_json`, `schema` and `http_<status>` are stored as the row's error code, never the model's words, and the batch goes on, however many errors come in a row (Review Focus 3); a failed connection or a 404 (model not pulled) stops the batch with no row so the window is tried again.
- Teacher pick (C14, C22, B12): windows assigned `suggested` whose text lives, with no suggestion row, no repeat and no owner label that names a question (a page cause-only note doesn't count, C1), soonest to expire first; the time moves on during a batch (`now` plus the monotonic time spent so far), a window is sent only if it still qualifies just before its call and gets a row only if it still qualifies just after, so text that expires during the batch is never sent and gets no row; the model is never called under the store lock.
- Training data (Task 8, C6, C12): one origin per model (`MixedOrigins` when the owner's (`aron`) and synthetic labels both exist and none is chosen; a row that names no question, such as a page cause-only note, gives no origin); train targets are the latest label per window and question from any project (page fixes included), grade targets only the owner's blind- and repeat-project labels (synthetic: every window), and a not-sure answer is never a target; only labels of the scheme's version are read.
- Splits: grouped by channel, channels shuffled by the seed; test channels are added until test holds at least `min(200, 20%)` of the windows and both Moment and ordinary windows, `picked_rare` windows on test channels leave every split (C21), then validation channels until 15% of the rest and both kinds; one channel is always left for validation and one for train, so a split needs 3 channels.
- Rung 0: `DictVectorizer` over the counted numbers and `emote:<id>` counts, then `MaxAbsScaler` (added: raw counts keep lbfgs from converging in 1000 iterations), then `LogisticRegression(max_iter=1000, class_weight="balanced")`.
- Rung 1: `TfidfVectorizer(ngram_range=(1, 2), min_df=2)` over one line per message, `@s<N>` written `@someone`, emote names kept as words (`emote_mode="id"` writes `emote_<id>`); the token pattern keeps `emote_<id>` and `@someone` whole, bigrams can span a line break, and windows without text are left out of rung 1's fit, thresholds and report.
- Heads: one per question; `doing` is one-vs-rest (values with p >= 0.5, else the top value; confidence = the lowest p chosen); a head that saw one class answers it with confidence 1.0, and a head with no training windows (or no word in 2 windows) never answers; `config` records both (C21).
- Thresholds: per question, the smallest of 0.30, 0.35 ... 0.95 at which answered agreement on graded validation windows is at least 80% with at least one answer; otherwise none, and the question is always "not sure".
- Metrics: per question on graded test windows; agreement is answered agreement (`doing`: exact set match) with a Wilson 95% interval; per-value precision over answered windows and recall over all graded windows (an abstention is a miss); macro-F1 over values that are in a label or an answer; `aron_not_sure_also_abstained` = (model abstained, owner not sure). Self-consistency compares the owner's first blind/suggested label with their repeat label where both answer.
- Rung-1 evidence: each line is scored alone; `doing` uses the value's decision function (w.x + b), a single-value question the class's coefficient row (w.x, C21); a line with no known word has no score; up to 5 lines scoring above 0, best first.
- Rung-0 evidence (C20): up to 5 lines that hold the emote IDs (or, for `question_share`, a `?`) with the largest positive coefficients for the value, on the scaled features.
- Manifest (Task 9): `model_id` is the first 12 hex characters of `model.joblib`'s sha256; `input_sha256` is the sha256 of the sorted `window_id|label_id|labels_version` lines (one per line, each ending in a newline) over the labels of the model's origin that name a question; `eligible_as_of` is the newest of the deletion checks and the export coverage (B7); `teacher` is the sorted `model/prompt_version` of suggested labels used; `self_consistency` sits beside `report` (C28); `versions` holds Python and library versions. No chat text, only window IDs and counts.
- Labels changed: `manifest.write` refuses (`LabelsChanged`) when the labels in the store no longer give the targets the model was trained on, so `input_sha256` always describes the training labels.
- Retiring (C16): writing a model retires every other unretired model of the same rung and origin; a model ID that already exists is re-activated (its row keeps `created_at`) rather than inserted again.
- Model files: always found as `<data>/models/<model_id>/`, never at a stored absolute path (the `manifests` row keeps `<model_id>/model.joblib`), so a moved or copied data folder works on its own files only.
- Word models (C5): a rung >= 1 manifest records `text_message_counts`, the message count of every split window whose text it saw, and a deletion check records in `text_drops` the fewest messages each window it changed has held since. Expiry deletes the `model.joblib` once none of those windows has text, or as soon as one of them holds, or has held since a check, fewer messages than recorded (a deletion check reached it, even if that window's text has expired since), and on an unreadable manifest; it sets `file_deleted_at` and retires the model. Only files actually removed count as deleted; a model with neither file nor manifest in `models/` is reported as not found and left as it is. A file that can't be deleted is retired at once and retried on every expiry. The manifest stays. Commands that apply deletion checks run expiry again after them, also when a refused check file stops them.
- Model leftovers: expiry deletes a `.writing-*` dump in `models/`, and a `<model_id>/model.joblib` with no `manifests` row or whose row says its file was deleted, once it is at least 10 minutes old (so a write still running is left alone).
- Answering model: per question, among unretired models whose file exists in `models/`, owner-origin (`aron`) models when any exist, else synthetic; the newest model per rung; rung 1 replaces rung 0 only when its test-agreement Wilson lower bound is above rung 0's point estimate (no answered windows counts as 0).
- Predictions: one row per window with text and question, holding the raw answer (`doing` as a list) and its confidence; a question the model doesn't answer gets no row; retraining the same model ID replaces its rows.
- Moment page (Task 10a): FastAPI with Jinja templates, served by uvicorn on `127.0.0.1:14612` (`serve` refuses any other host but `localhost`; access log off). It answers only to the Host names `127.0.0.1` and `localhost` (DNS rebinding), refuses a POST whose `Origin` is another site or whose `Sec-Fetch-Site` is not same-origin (403; `Origin: null` passes only with `Sec-Fetch-Site: same-origin`, as a native form post can send it), and sends a `default-src 'self'` CSP with `frame-ancestors 'none'` and `Referrer-Policy: same-origin` (no referrer to other sites; the page's own posts keep their real `Origin`). No outbound requests: CSS, script and fonts come from `static/`.
- Page fonts: Geist and Geist Mono, latin variable `woff2` (weights 100–900), copied from an earlier private prototype, which packed them from `@fontsource-variable/geist` and `@fontsource-variable/geist-mono` (the version is not recorded there), SIL OFL 1.1 (licences beside the files). SHA-256: `geist-latin-wght-normal.woff2` 19f9c92546aa300c312235e3125af1b81394d8db9a4bc4a425cd5b641d2d54e1, `geist-mono-latin-wght-normal.woff2` 684ad5b531f81d43c1e8c7038262d5db7cdc1f68006e04d6c7769efa8d33c8cc, `OFL-geist.txt` 71609cbb5c78b5870d712eab73a31d76622635c6ed034ab5cee3b9ecbda8685f, `OFL-geist-mono.txt` cc815ed4fc045f0e991abb10395b7932bd028c6a067deb13316d6002105074e6.
- Page colours: light is an earlier private prototype's light palette; dark is its "Deep" dark palette (the picked dark look); the accent is `#7553FF`. Colours raised to 3:1 by lightness alone: the light curve `#A29FAA` (2.60:1 on white) to `#8F8B98` (3.33:1 on white, 3.13:1 on `#F8F8F9`); in Deep dark, against `#14131A`, chart 2 `#5D3EB2` (2.46:1) to `#6B4CC0` (3.01:1), chart 3 `#50219C` (1.79:1) to `#773DD6` (3.01:1), chart 4 `#7C2282` (2.12:1) to `#A02CA8` (3.01:1) and the other colour `#534D5E` (2.28:1) to `#665F74` (3.04:1). The light chart colours are unchanged.
- Page look: the approved BrainChat look: the Thread layout, the Deep dark palette with a light theme, and Geist and Geist Mono self-hosted, on the `--cb-*` color, type, spacing and radius tokens in `page.css`. The theme follows the OS, and the top bar's switch sets `<html data-theme>`. The product name is BrainChat, with no other product's logo, wordmark or icons.
- Shown answer (C1): per question, the owner's latest label naming it (any project, `created_at` then `id`); else the answering model's newest prediction (rung 0's when the answering rung-1 model has none for the window), shown only at or above that model's threshold for the question; "not sure" otherwise, with the reason (no chat, needs review, no model yet, no prediction yet, no threshold, or under threshold with both numbers). A model answer for a window with at most one message is "no chat in this window" whatever its confidence; the owner's labels always stand.
- Needs review (C19): a window whose counted `emote_counts` holds an ID in `config/review_emotes.json` shows every answer that isn't the owner's label as not sure, needs review. The list is read at page start.
- Text on the page (C19): chat lines, evidence lines and the chart show only while `text_state` is `present` and `text_expires_at` is after the request's clock, so nothing shows past expiry between the hourly runs.
- Page writes (B24, B31): `POST /m/<id>/fix` and `/cause` each add one label row (project `page`, origin `aron`, the owner's own labels, provenance `corrected-on-page`, the scheme's versions); a cause row carries only the cause note and source. Both refuse (409) while the deletion check is stale. The page's other writes are expiry and the rung-0 backfill, at start and hourly.
- Page times (B28): clock times are local (`astimezone()`); chat lines and the chart use offsets from the Moment's anchor with a true minus sign.
- Asking with the local model (Task 10c): the keyword answer (10b) is stored and shown first; the page script then posts `POST /ask/<id>/model` once per step, one ask at a time in page order, and swaps in the answer block the server sends back. Without the script the keyword answer stays. `page --no-model` builds no narrator and shows the 10b banner.
- Step 1 (read): `qwen3:8b` by default (`page --model` for others) through a streamed `POST /api/chat` with `format` = `query.schema(...)` (B34: an empty enum is written as `null`), `think` false, temperature 0, `num_ctx` 8192, at most 512 output tokens and `keep_alive` 30m; prompt version `cb_ask_2026_11_09_v1` (`cb_ask_2026_11_07_v1` until the BrainChat rename and the owner wording changed the prompt text). The prompt holds the rules, the scheme, worked examples, the previous query and the previous rows as `#n = channel clock value`; chat text never enters it. The reply goes through `query.check` like the keyword parse. A different valid query swaps the chips (marked "refined by the local model") and SQL runs again on it; the same query, or a reply that is unusable or not strict JSON, keeps the keyword chips; a refusal stores `[refused: <reason>]`. Editing a chip skips step 1.
- Step 2 (caption): only for one Moment (a Moment or evidence block), an emote's meaning (a mix block over at least `EMOTE_MIN` windows) or a vague question answered by the default reading; never for a list, a count by filter, a refusal or "can't answer". Its input is the chips in words, numbered facts from the answer on screen, the not-sure answers, the cause note and up to 5 of the Moment's evidence lines without speakers; never the question. A caption is at most 3 sentences with numbers and channels only as slots and `[n]` citations to the Moments on screen; any failed sentence check drops it and the template line stays.
- Caption storage: the checked caption is stored in `asks.summary` with the facts, citations and evidence message IDs it was written for (`notes.caption_for`); a caption whose facts no longer match the answer on the page, or whose evidence lines are not all still stored, is hidden as stale. A caption can repeat a chat line, so a deletion check that drops messages from a window clears the caption of every ask over that window in the same transaction (`ingest.apply_deletion_check`), and a caption whose line a check dropped while it was being written is not stored. A model step rewrites the row with `store.update_ask` and keeps 10b's expiry rule (B26).
- Fallbacks: Ollama off, older than 0.31.2, the model not pulled or a base URL that isn't loopback keep the keyword answer and show the amber banner with its fix (`ollama serve`, update, `ollama pull <model>`, this PC only). A step-1 timeout (20 s on the GPU, 60 s on the CPU) keeps the keyword answer and marks the model as timed out for 30 s (the state cache), with the banner "didn't answer in time".
- CPU: `/api/ps` showing the model with less than half of it in GPU memory counts as CPU. The dock says "about half a minute per answer", captions are off unless `page --cpu-captions`, and a waiting step adds "Still working" after 10 s.
- Preload: once per page start, in a thread, only when the model's state is usable: an empty chat with `keep_alive` 30m. Building the page (and `page` itself) asks Ollama nothing.
- Token flow: the owner makes the Label Studio token in its own UI and writes it to `<data>/.env`; only the CLI reads that file, only on the real data folder, and sends the token only to the loopback Label Studio (refreshed as above); no output, error or log line carries it, and agents never read `.env`.
- Deletion report (spec section 12, C29): `window-list` writes the IDs of every window that still has text, the server's check script answers with a `chatbrain-deletion-check/1` file of the message IDs still there, and `deletions` (or `ls-push`, `suggest` and `train`, which apply waiting check files first) drops the rest, recounts, and runs expiry so Label Studio tasks and word models that held the dropped lines go too.
- Expiry runs at the start of every command (`ask-eval` excepted: it reads no stored data), at page start and hourly while the page runs; it runs only when something runs, so before P1 the owner sets up a daily Windows Task Scheduler job that runs `uv run chatbrain expire` from this folder with `CHATBRAIN_DATA` set (C27).
- `expire` exits 1 while text that is due to go may still be held: Label Studio unreachable or refusing (also when it could not check for tasks the store lost track of), task deletions or a compaction pending (an export copy that could not be deleted keeps one due), a word-model file not deleted yet or missing, or a file in `<data>/inbox` or an import source left in place that is past its text expiry. Every command prints the inbox and source counts (counts only); nothing deletes an inbox file for the owner (B10), who imports or deletes it. The owner watches the scheduled task's Last Run Result in Task Scheduler (anything but `0x0` needs a look), or turns on its history (Enable All Tasks History) to see every run.
- Chunking and pooling: not needed until rung 2. Rungs 0-1 read a whole window (counts, or one TF-IDF document), and the teacher sends the whole window with `num_ctx` 8192, so a very busy window can be cut short by Ollama; watch for that in the P1 pilot.
- Spec deviation (C25): spec section 11's P0 export command (against a local database) is not here: the real export script lives on the StreamPulse server and is not part of this repo; `fake.make_export` and `docs/export-format.md` stand in for it.
- Demo (Task 11): `demo --seed S` works in `<data>/demo`, its own data folder and store, on the real clock (C17), and deletes the last demo's files first, once Label Studio holds none of that demo's tasks and no delete waits for compaction; its steps call the same command functions as the CLI, the teacher through `teacher.run` (B17).
- Demo showcase (B3, B25): `fake.make_showcase` adds one short stream on `fakechan13` ending 2 hours before now, with fixed lines per window (a chant, repeated emotes, a back-and-forth, two critical turns, a shocked and an unclear Moment, two ordinary windows), so the page's newest stream has those spreads; its answers come back through `fake.truth` like every made-up window.
- Demo Label Studio (B20, C18): the demo's projects are titled `BrainChat demo · Suggested`, `· Blind` and `· Repeat`, which the real projects' exact-title lookup never finds, so the real store never adopts or pulls a demo task; suggested tasks need a suggestion (3 with `--with-ollama`, else none), 10 repeat rows are made due now so 10 repeat tasks go in with no prediction and no earlier label (`schedule_repeats` is unchanged), and every demo task is pulled, deleted and compacted before the demo ends.
- Demo sentinel search (B15, B16): after expiry the demo reads every file under the data folder for expired windows' marker lines, Label Studio's folder for deleted tasks' marker lines, and Ollama's `*.log` files for the marker lines of windows it sent; links are not followed, counts only are printed, and any hit or unreadable file makes the demo exit 1.
- Stop: the route writes the stopped outcome first, under the ask lock, then sets the step's stop event, which the stream reader checks between chunks, so a late model result is never written after Stop and a stop survives a restart. Esc stops the running step when no menu or panel is open.
- Model logs (`chatbrain.ask`, `chatbrain.narrator`): step, outcome, intent, validator codes, result count, milliseconds and `eval_count`; never the question, a prompt or model output. `OLLAMA_DEBUG` is never set.
- `ask-eval`: reads `tests/data/ask_questions.json` against a made-up three-channel world in a temporary folder and prints exact intent and exact filters for the local model and the keyword path, the bar (90% intent, 75% filters) and failure codes; never a question or model output. It runs no expiry, needs the Ollama gate and never preloads.
